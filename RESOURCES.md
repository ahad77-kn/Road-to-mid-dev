## 6 · State — the concept that runs through everything

"State" just means *the data your app currently holds, and who is allowed to change it*. It shows up at four levels and beginners confuse them constantly.

| Level | What it is | Where to read |
| --- | --- | --- |
| **UI state** | is the menu open, which tab is active | [react.dev: State — a component's memory](https://react.dev/learn/state-a-components-memory) |
| **Shared / lifted state** | two components need the same value | [react.dev: Sharing state between components](https://react.dev/learn/sharing-state-between-components) |
| **Server state** | data that lives in a database and you *copy* into the browser | [react.dev: Synchronising with effects](https://react.dev/learn/synchronizing-with-effects) · [TanStack Query overview](https://tanstack.com/query/latest/docs/framework/react/overview) |
| **Session / auth state** | who is logged in, and for how long | [The Copenhagen Book: Sessions](https://thecopenhagenbook.com/sessions) |

Also read:
- [react.dev: Choosing the state structure](https://react.dev/learn/choosing-the-state-structure) — the single most useful page on state

## 8 · Auth — sessions, tokens, guards

This is the part most self-taught developers get wrong, and it is exactly what interviewers probe. Read the whole section before Week 21.

| Topic | Link |
| --- | --- |
| **Start here — the clearest free auth book** | [The Copenhagen Book](https://thecopenhagenbook.com/) — sessions, passwords, tokens, MFA, in plain language |
| Password hashing (never store plain passwords) | [OWASP: Password storage cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [bcrypt](https://www.npmjs.com/package/bcrypt) |
| Sessions vs JWT — the real trade-off | [Copenhagen Book: Sessions](https://thecopenhagenbook.com/sessions) · [OWASP: Session management cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) |
| What a JWT actually is | [jwt.io introduction](https://jwt.io/introduction) |
| Why "just put the JWT in localStorage" is a bad default | [OWASP: HTML5 security — local storage](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage) |
| Cookies: `HttpOnly`, `Secure`, `SameSite` | [MDN: Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie) |
| Access + refresh tokens | [Auth0: Refresh tokens](https://auth0.com/docs/secure/tokens/refresh-tokens) |
| **Authentication vs authorisation** | [Auth0: AuthN vs AuthZ](https://auth0.com/intro-to-iam/authentication-vs-authorization) |
| Route guards / protected routes (frontend) | [React Router: protected routes](https://reactrouter.com/start/framework/route-module) — remember: a frontend guard is UX, **not** security |
| Auth middleware (backend — the real guard) | [Express: writing middleware](https://expressjs.com/en/guide/writing-middleware.html) |
| Role-based access control | [OWASP: Authorization cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) |
| OAuth & "Login with Google" | [OAuth 2.0 simplified](https://www.oauth.com/) |

**The three sentences to memorise:**
1. *Authentication* = who are you. *Authorisation* = what are you allowed to do. Different problems, different code.
2. A hidden button is not security — every protected route must be checked **again on the server**, on every request.
3. Never store a plain password. Ever. `bcrypt`/`argon2`, always.

## 📌 How to read documentation (a skill on its own)

1. **Skim the page structure first** — headings tell you what exists before you read a word.
2. **Type the example**, do not read it. Change one value. Predict what happens *before* you refresh.
3. **When stuck, read the error message fully** — all of it, including the file and line number. Most beginners read the first three words and guess.
4. **Search like a developer:** `mdn flex-shrink`, `express middleware error handling`, `mongoose populate not working`. Add the tool name, not "how do I".
5. **MDN over blog posts.** Blog posts age badly; MDN and the official docs are maintained.
